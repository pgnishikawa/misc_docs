# 4. ソフトウェア設計とブリングアップ

[← 目次](README.md)

## 4.1 まず決めること：スレーブスタックを自作しない

EtherCAT スレーブのアプリケーション層（AL 状態機械、メールボックス処理、CoE オブジェクト
ディクショナリ、SDO/PDO 処理など）をフルスクラッチで実装するのは、レジスタ経由の
バイトI/Oを書くのとは比較にならない工数がかかります。業界では通常、以下のいずれかを使います。

| 選択肢 | 特徴 |
|---|---|
| **Beckhoff SSC (Slave Stack Code)** | EtherCAT Technology Group (ETG) 会員向けに提供される公式リファレンス実装。ET1100 を含む Beckhoff ESC 向けの HAL 層サンプルが付属。ETG membership とライセンス同意が必要 |
| **SOES (Simple Open EtherCAT Slave)** | オープンソース（GPL/商用ライセンス選択可）のスレーブスタック。ET1100 含む複数 ESC に対応した実績あり |
| **その他商用スタック** | 各社が ESC 抽象化層＋CoE/FoE 実装を製品として提供 |

いずれを選んでも、**RZ/N2L 側でアプリケーションが実装すべきなのは「ESC のレジスタ／メモリに
16bit 単位で読み書きするだけの薄いハードウェア抽象化レイヤ（HAL）」**です。本章では、
そのHALが満たすべき要件と、スタックを使わない場合の最小実装の考え方の両方を示します。

> 上記スタックの入手・ライセンス条件・API 仕様は本リポジトリの資料には含まれていません。
> 採用する場合は各プロジェクトの配布物・ドキュメントを別途参照してください。

## 4.2 ハードウェア抽象化レイヤ（ESC HAL）に必要な最小関数

`03_rzn2l_bus_interface.md` の方式Aを前提とすると、最低限これだけあれば大抵のスタックの
ESC 抽象化インタフェースを満たせます。

```c
uint16_t esc_read16 (uint16_t esc_addr);
void     esc_write16(uint16_t esc_addr, uint16_t value);

void esc_read (uint16_t esc_addr, void *dst, uint16_t len);   /* len は偶数を推奨 */
void esc_write(uint16_t esc_addr, const void *src, uint16_t len);
```

- `esc_addr` は ET1100 のレジスタ/RAM アドレス（0x0000〜0x2FFF 等）。
- `esc_read`/`esc_write` は内部で `esc_read16`/`esc_write16` をループするだけでよい
  （境界が奇数長になる場合のみ、末尾を read-modify-write）。
- **これらの関数の中身以外に EtherCAT 固有のロジックを持ち込まない**のがコツです。
  状態機械やメールボックス解釈はスタック（または上位アプリ）側に任せます。

## 4.3 起動シーケンス（RZ/N2L 側）

```
① 電源投入・RZ/N2L 自身の初期化（クロック、BSC/外部バス設定、GPIO/割り込み設定）
② ET1100 の PDI 有効化待ち
     - 0x0110[0] (ESC DL status: PDI operational) が 1 になるまでポーリング
       （タイムアウトは数百ms、02章2.6節参照）
     - EEPROM_LOADED 信号を使える場合はそれも合わせて確認
③ 基本情報の読み出し（デバッグ・検証用）
     - 0x0000 Type, 0x0001 Revision, 0x0004 FMMUs supported, 0x0005 SyncManagers supported
       等を読み、期待値（FMMU=8, SM=8 等）と一致するか確認 → 配線・タイミング設定の健全性チェックになる
④ AL status を読み、Init 状態であることを確認（通常 EEPROM ロード後は自動的に Init）
⑤ 割り込み設定（4.5節）
⑥ メインループ／スレーブスタックの初期化関数を呼び出す
     - 以降は AL control の変化・メールボックスイベント・プロセスデータ周期処理を
       スタック（または自作の状態機械）に委ねる
```

**手順③は必須ではありませんが強く推奨します。** 期待値と異なる値が読めた場合、
EtherCAT の知識よりも先に「バス配線・タイミング設定が間違っている」可能性を疑えるからです
（例：`0x0004` が `8` ではなく `0x00` や `0xFF` に張り付く場合、CS/RD/WR/WAIT の
どれかが誤っているサイン）。

## 4.4 AL 状態機械への応答（自作する場合の最小実装イメージ）

スレーブスタックを使わずポーリングだけで最小限の応答をする場合の骨子（あくまで概念例）：

```c
uint16_t al_control = esc_read16(0x0120) & 0x000F;
uint16_t al_status  = esc_read16(0x0130) & 0x000F;

if (al_control != al_status) {
    switch (al_control) {
    case 1: /* Init へ */
        /* メールボックス/プロセスデータの後始末 */
        esc_write16(0x0130, 1);
        break;
    case 2: /* Pre-Op へ */
        /* SyncManager 0/1 (メールボックス) の設定を読み、妥当なら遷移 */
        esc_write16(0x0130, 2);
        break;
    case 4: /* Safe-Op へ */
        /* SyncManager 2/3 (プロセスデータ) の設定を読み、妥当なら遷移 */
        esc_write16(0x0130, 4);
        break;
    case 8: /* Op へ */
        esc_write16(0x0130, 8);
        break;
    default:
        /* 遷移不可: エラー表示 */
        esc_write16(0x0130, (uint16_t)(al_status | 0x0010));
        esc_write16(0x0134, /* AL status code */ 0x0011 /* 例: Invalid requested state */);
        break;
    }
}
```

実際にはこれに加えて、SyncManager の Activate ビット監視（`0x0800 + N*8 + 0x06`）、
CoE オブジェクトディクショナリの整合性チェックなど、状態遷移の可否判定が必要になります。
**この判定ロジックの実装量が大きいため、4.1節のスタック利用が現実的**です。

## 4.5 割り込み設計

- ET1100 の `IRQ` はレベルトリガです（`02_et1100_overview.md` 2.8節）。RZ/N2L の対応する
  外部割り込み入力を **レベル検出（Low レベルなど、極性は EEPROM 設定に合わせる）**に
  設定できるなら、それが最も安全です。
- 本リポジトリの FSP では、外部割り込みドライバ `r_icu`（`external_irq_api_t`）が
  トリガ種別 `EXTERNAL_IRQ_TRIG_LEVEL_LOW` をサポートしています
  （`r_external_irq_api.h`、`02_et1100_overview.md` 2.8節）。ET1100 の `IRQ` を
  active low のまま接続する場合は、これを選んで `open()` してください。
  ISR（コールバック）側では前段のイベント処理が終わるまで `AL event request` を
  読み続け、要因がゼロになったことを確認してから戻る実装にします
  （レベルトリガなので要因が残っていれば ISR は即座に再度呼ばれます／あるいは
  無限ループにならないよう、要因がゼロになるまでその場でループする実装のどちらかを選びます）。
- エッジ検出しか使えない場合は、**ISR の最後に必ず `AL event request (0x0220:0x0223)` を
  読み、非ゼロなら該当ビットを `AL event mask` との整合を取りつつ処理し切ってから
  ISR を抜ける**実装にしてください（Section I 18.13.1、`02_et1100_overview.md` 2.8節）。
- `AL event mask (0x0204:0x0207)` で、アプリケーションが処理したい要因だけを
  有効化してください（未使用要因を立てたままにすると不要な割り込みが飛び続けます）。
- ポーリングと割り込みを同じ要因に対して併用しない（取りこぼしの原因、Section I 18.13.2）。

## 4.6 EEPROM/ESI の作成

1. **PDI 種別を確定**：`0x08`（16bit非同期）か `0x09`（8bit非同期）かを、
   `03_rzn2l_bus_interface.md` の結線方式に合わせて決める。
2. **Configuration Area A/B の値を作成**：`BUSY`/`IRQ`/`BHE`/`RD` の極性・ドライバ種別、
   DC 使用有無などを決める。`et1100_configuration_and_pinout_v4.7.xls`
   （Beckhoff 提供ツール）を使うと、選択したピン構成に応じた設定値を機械的に導出できます。
3. **ESI 情報を作成**：Vendor ID・Product Code・Revision・Serial Number、
   SyncManager/FMMU のデフォルト構成、Object Dictionary（CoE を使う場合）などを
   ETG.2000 (ESI 仕様) に従って作成します。多くの場合、採用するスレーブスタックの
   ツールチェイン（ESI エディタ等）がこの作成を支援します。
4. **同じ内容を2箇所に反映する**ことを忘れない：
   - 物理 EEPROM（ET1100 に接続、I²C）へバイナリを書き込む
   - マスタが読み込む **ESI XML ファイル**（TwinCAT 等のマスタ設定ツールに登録）
   両者の Vendor ID/Product Code/Revision が一致しないと、マスタがスレーブを
   正しく識別できません。
5. **★初回（工場出荷時、EEPROMが完全にブランクの状態）は、ET1100を`RESET`状態に保持したまま
   外部I²Cライタで`EEPROM_CLK`/`EEPROM_DATA`に直接書き込むこと。** ブランクEEPROMのままでは
   PDI（RZ/N2Lとの非同期バス）自体が有効化されず、`02_et1100_overview.md` §2.7.1で説明する
   「PDIレジスタ経由でEEPROMを書く」方法は**初回には使えない**（PDIがまだ生きていない）。
   RZ/N2L経由の書き込みは、この初回書き込みで有効なPDIが立ち上がった後の更新にのみ使う。
   全体の順序は[06_implementation_roadmap.md](06_implementation_roadmap.md) Phase 3を参照。
6. EEPROM 書き込み後は **10秒以内に電源断・リセットしない**（`02_et1100_overview.md` 2.7節）。

## 4.7 CoE オブジェクトディクショナリと PDO マッピング（実装イメージ）

CoE を使う場合、RZ/N2L 側は「メールボックス経由の SDO 要求（オブジェクトの読み書き）に
応答する」処理と、「PDO マッピングで指定された通りにプロセスデータ RAM を並べる」処理の
2つを意識することになります。**正式なプロトコル仕様（ETG.1000.6）は本リポジトリには
含まれていない**ため、以下は一般的な EtherCAT CoE の実装で広く使われている考え方の
概要です（採用するスレーブスタックが多くの部分を代替してくれます）。

- **オブジェクトディクショナリ (OD)** は `インデックス(16bit):サブインデックス(8bit)` で
  引くテーブルです。アプリケーションは C 側で「インデックス→変数へのポインタ・型・
  アクセス権」の対応表（OD テーブル）を持ち、SDO 要求が来たらこの表を引いて応答します。
- **PDO マッピングオブジェクト**（慣例的に RxPDO は `0x1600`〜、TxPDO は `0x1A00`〜）は、
  「どの OD エントリを、プロセスデータのどのビット位置に配置するか」を記述します。
  マスタはこのマッピング情報（EEPROM/ESI のデフォルト、または起動時に CoE 経由で
  マスタが変更したもの）に従って SM2/SM3 のバッファレイアウトを決定します。
- **実装上のコツ**：アプリ側の入出力データを表す C 構造体を1つ定義し、
  その構造体のオフセットが PDO マッピングで宣言した並び順・幅と一致するようにします。
  こうすれば `esc_read`/`esc_write` は単純に「その構造体サイズ分をプロセスデータ RAM の
  該当オフセットとの間でコピーする」だけの実装で済みます。
  ```c
  typedef struct {
      uint16_t status_word;
      int32_t  actual_position;
  } __attribute__((packed)) txpdo_t;   /* TxPDO: スレーブ→マスタ (SM3 側) */

  typedef struct {
      uint16_t control_word;
      int32_t  target_position;
  } __attribute__((packed)) rxpdo_t;   /* RxPDO: マスタ→スレーブ (SM2 側) */
  ```
  （構造体のバイト整列とビットフィールドの並びが `uint16_t` 境界に揃うよう、
  `03_rzn2l_bus_interface.md` 3.4節の制約と合わせて設計してください。）
- **Emergency メッセージ**（異常発生時にスレーブからマスタへ通知する固定フォーマットの
  メッセージ）や、SDO の segmented transfer（大きなデータの分割転送）など、
  細かいプロトコル差異は採用するスタックのドキュメントに従ってください。

## 4.8 プロセスデータ（周期データ）の扱い

- プロセスデータ RAM（`0x1000`〜、8KB）は SyncManager 2/3 経由でマスタと交換されます。
- レイアウト（どのバイトが入力でどのバイトが出力か）は EEPROM の SM/PDO 設定と
  マスタ側 ESI/ENI 設定で決まります。**RZ/N2L 側アプリケーションは、決められたオフセットに
  対して `esc_read`/`esc_write` するだけ**です。
- 3.4節で述べたとおり、**このメモリ領域も含めて `uint16_t` 境界でアクセスする**運用にすれば、
  方式A（`ADR[0]`/`BHE` 固定）の制約とも矛盾なく設計できます。アプリケーションの
  プロセスデータ構造体は `uint16_t` 配列またはメンバを2バイト境界に揃えた構造体にしてください。
- SyncManager バッファの開始アドレスは **8バイト（64bit）境界に揃えることが推奨**されています
  （Section I 第8章）。

## 4.9 ウォッチドッグと周期処理のタイミング予算

ET1100 は **プロセスデータウォッチドッグ**（`0x0420:0x0421` で周期を設定、
`0x0440:0x0441`/`0x0442` で状態・カウンタを確認）と **PDI ウォッチドッグ**
（`0x0410:0x0411`、`0x0443`）を持ちます（`05_register_reference.md` 5.9節）。
これは「マスタ（またはPDI）が一定時間アクセスしてこなかったら異常とみなす」仕組みで、
タイムアウトすると出力が既定値にクリアされる等の安全動作が働きます。

ソフトウェア設計として意識すべき点：

- **RZ/N2L のプロセスデータ処理ループ（メインループ or 周期タスク）は、設定した
  PDI ウォッチドッグ周期よりも確実に短い周期で SyncManager バッファへアクセスできる
  ことを保証してください。** 割り込み処理やより優先度の高いタスクにブロックされて
  処理が遅延すると、ウォッチドッグが意図せず発火し、出力がクリアされる／
  `AL status` にエラーが出る、といった現象が起きます。
- 逆に、PDI 側からのウォッチドッグが不要な用途（例：出力を持たない、または
  安全機構を上位で別途持っている）であれば、`0x0410:0x0411` を無効値に設定して
  ウォッチドッグ自体を使わない選択肢もあります（詳細な無効化条件は
  Section I 第13章「Watchdogs」を参照）。
- EtherCAT 全体の通信サイクルタイム（マスタが何ms/µs周期でフレームを送るか）と、
  RZ/N2L 側のプロセスデータ処理周期は独立して設計できますが、**RZ/N2L 側の処理が
  マスタの通信サイクルより遅いと、マスタから見て「データが更新されていない」状態が
  発生**します。要求される制御周期（例：1ms制御なら1ms未満での処理完了）を
  早い段階でシステム要件として確定し、3.5節のバスアクセス時間（ウェイト込みの
  1レジスタアクセスあたりの所要時間）を積算して、間に合うかどうかを見積もってください。

## 4.10 開発・検証用の EtherCAT マスタとツール

ここまでの手順を実際に試すには、**EtherCAT マスタ**（対向機器）が必要です。
量産で使うマスタ製品がまだ決まっていなくても、開発初期の疎通確認には以下のような
選択肢が一般的に使われています（いずれも本リポジトリの資料には含まれていない
一般的な業界ツールです。ライセンス条件は各ツールの配布元を確認してください）。

| ツール | 位置づけ |
|---|---|
| **TwinCAT (Beckhoff)** | Windows PC を EtherCAT マスタにする商用ソフト。Engineering版は無償利用枠があり、ESI XML の読み込み、AL 状態遷移操作、レジスタ/CoE のモニタが GUI から可能。事実上の業界標準デバッグ環境 |
| **IgH EtherCAT Master** | Linux カーネルモジュールとして動作するオープンソースマスタ。実運用にも使われる |
| **SOEM (Simple Open EtherCAT Master)** | オープンソースのユーザ空間マスタライブラリ。軽量で組み込みLinux等からの制御実験に向く |
| **Wireshark + EtherCAT dissector** | PC の NIC でフレームをキャプチャし、EtherCAT コマンド／データグラム／ワーキングカウンタをパケット単位で解析できる。**プロトコルレベルの不具合切り分けに非常に有効** |

**推奨する使い方**：まず PC + TwinCAT（または IgH/SOEM）を EtherCAT マスタとして用意し、
RZ/N2L 側の実装が `Init → Pre-Op → Safe-Op → Op` まで遷移できるかを確認します。
うまくいかない場合は Wireshark でフレームをキャプチャし、マスタが送ったコマンドに対して
ワーキングカウンタ（Working Counter）が期待通り増えているか（＝スレーブが実際に
応答しているか）を見ることで、「バスの物理的な疎通問題」なのか「AL状態機械/CoEの
ロジックの問題」なのかを切り分けられます。

## 4.11 ブリングアップ手順（推奨する検証の順序）

1. **バス単体の疎通確認**：ET1100 の `0x0000`(Type)〜`0x0009` を読み、既知の値
   （FMMU=8, SM=8, RAM=8等）と一致するか確認。一致しなければ配線・BSCタイミング設定を疑う。
2. **EEPROM ロードの確認**：電源再投入を数回行い、毎回 `0x0110[0]` が安定して1になるか、
   異常終了（EEPROM CRC エラー等）が出ないか確認。
3. **単体でのレジスタ read/write 確認**：`0x0F80`-`0x0FFF`（User RAM、EtherCAT機能に
   影響しない領域）に対して読み書きし、書いた値がそのまま読めるかを確認
   （バス・タイミング・グルーロジックの健全性チェックに最適）。
4. **AL 状態機械の疎通**：EtherCAT マスタ（4.10節参照。TwinCAT 等）と接続し、
   Init → Pre-Op まで遷移できるか確認（メールボックス通信の疎通確認を兼ねる）。
5. **プロセスデータ疎通**：Safe-Op → Op まで遷移し、周期データが期待通り読み書きできるか確認。
6. **異常系**：ケーブル抜去、マスタ側からの強制リセットコマンド（`0x0040`）、
   ウォッチドッグタイムアウトなどを意図的に発生させ、RZ/N2L 側が復帰できることを確認。

## 4.12 よくあるハマりどころ（データシート記載の既知事項）

| 症状 | 原因の可能性 | 参照 |
|---|---|---|
| `0x0004`等の基本情報が読めない/化ける | バス配線・CS/RD/WR/WAIT タイミング不整合、`ADR`の1bitオフセット漏れ、CS空間がキャッシュ可能属性のまま | `03_rzn2l_bus_interface.md` 3.6/3.9節 |
| 割り込みが最初の1回しか発生しない | エッジトリガ設定＋ISR内でAL event requestを読み切っていない | 本書 4.5節 / Section I 18.13.1 |
