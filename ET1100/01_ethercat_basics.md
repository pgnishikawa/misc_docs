# 1. EtherCAT の基礎知識

[← 目次](README.md)

EtherCAT を全く知らないソフトウェアエンジニアが、ET1100 の仕様書を読んだときに
迷わないようにするための最低限の予備知識です。詳細は Section I – Technology
（`ethercat_esc_datasheet_sec1_technology_v2.5.pdf`）を参照してください。

## 1.1 EtherCAT とは（フレームが通り過ぎながら処理される）

EtherCAT は標準の IEEE 802.3 Ethernet フレームを使うフィールドバスです（Section I 冒頭）。
最大の特徴は、**マスタが送信した1つの Ethernet フレームが、複数のスレーブ（ET1100 等）を
データリンク層で数十〜数百 ns 程度の遅延だけで通過しながら、通過中にリアルタイムで
読み書きされる**ことです。一般的な Ethernet 機器のようにフレームを受信 → CPU が処理 → 再送信、
という遅いソフトウェア処理を挟みません。この「フレームを通過させながら読み書きする」処理は
ET1100 内蔵の ASIC ロジック（Fieldbus Memory Management Unit = **FMMU** と **SyncManager**）が
行い、**ホスト側の RZ/N2L ソフトウェアはこのリアルタイム処理には一切関与しません**。

RZ/N2L 側ソフトウェアが担当するのは、

1. ET1100 の内部メモリ（プロセスデータ RAM、レジスタ）に対する読み書き
2. スレーブとしての状態遷移・エラー処理・メールボックス通信（設定変更など低頻度の通信）

の2つだけです。ここを理解しておくと、以降の章で「なぜレジスタ経由でしかやり取りしないのか」が
腑に落ちます。

## 1.2 ネットワーク構成：マスタ1台・スレーブ複数・デイジーチェーン

- EtherCAT は **1台のマスタ**（PC/PLC 上のソフトウェア）と、**複数のスレーブ**（ET1100 のような ESC を搭載した機器）で構成されます。
- スレーブは通常デイジーチェーン（ライン/ツリー/リング状）で接続され、フレームは折り返して戻ってきます。
- ET1100 は **2〜4 ポート**を持ち（Section III Table 4）、複数ポートで物理的な配線トポロジを構成できます。今回の RZ/N2L 接続の主眼は「ホスト側 PDI」なので、ポート数・PHY 選定はハードウェア設計側の話として `02_et1100_overview.md` で簡単に触れます。

## 1.3 アドレッシング：スレーブをどう指定するか

EtherCAT のデータグラムは主に次のアドレッシング方式を持ちます（Section I 該当章）。

- **位置アドレッシング（Position addressing）**：ネットワーク上の物理的な順番でスレーブを指定
- **ノードアドレッシング（Node/Station addressing）**：`0x0010:0x0011` の Configured Station Address で指定
- **論理アドレッシング（Logical addressing）**：**FMMU** を介して複数スレーブのデータを1つの論理アドレス空間にマッピングし、1コマンドで一括アクセス（周期データ交換の主役）
- **ブロードキャストアドレッシング**：全スレーブに一括アクセス

ソフトウェアエンジニアとして意識すべきは **論理アドレッシング + FMMU** です。マスタは
「論理アドレス空間の特定範囲を読み書きする」という1つのコマンドを送るだけで、各スレーブの
FMMU がそれぞれ担当範囲を判断して自分の物理メモリ（プロセスデータ RAM）に読み書きします。

### 1.3.1 データグラムの中身は「プロセスデータ」「メールボックス」だけではない

1つの Ethernet フレームには複数の **EtherCAT データグラム**（コマンド）を積めます
（Section I 2.3「EtherCAT command types」）。各データグラムは「コマンド種別」と
「アドレス」を持ち、**アドレスの解決先が何であるかによって、実際に読み書きされる中身は
3種類に分かれます**。

| コマンド種別（例） | アドレス指定方式 | 実際の宛先 |
|---|---|---|
| `APRD`/`APWR`（位置）、`FPRD`/`FPWR`（ノード）、`BRD`/`BWR`（ブロードキャスト） | 固定オフセットアドレス | **任意の ESC レジスタ**（AL control/status、FMMU/SM 設定、SII EEPROM インタフェース、エラーカウンタ 等）または **メールボックスの SM バッファ** |
| `LRD`/`LWR`/`LRW` | 論理アドレス（FMMU 経由） | **プロセスデータ**（周期I/O、いわゆる共有メモリ的な部分） |
| `ARMW`/`FRMW` | 固定オフセットアドレス（DC レジスタ狙い） | **Distributed Clocks の時刻同期**（複数スレーブへ一括配信） |

つまり「プロセスデータ」と「メールボックス」は、EtherCAT の通信手段のうち
**アプリケーションが能動的に関わる2種類**にすぎません。実際にはこれと同じ仕組み
（固定オフセットアドレスへの読み書き）を使って、マスタは起動時に FMMU/SM の設定を書き込んだり、
AL control で状態遷移を要求したり、EEPROM インタフェースを操作したりしています
（[04_software_bringup.md](04_software_bringup.md) で扱う内容の多くはこちら側です）。

**RZ/N2L（PDI側）からは、どの EtherCAT コマンドで来たかは区別できず、
「自分のローカルメモリのどのアドレスが変化したか」しか見えません。** アドレスが
`0x0120`（AL control）なら状態遷移要求、SM バッファのアドレスならメールボックス、
FMMU がマッピングしているプロセスデータ領域ならプロセスデータ……という具合に、
**「何が起きたか」はアドレスだけで決まり**、コマンド種別の違いを意識する必要はありません。

## 1.4 FMMU（論理アドレス⇔物理アドレス変換）

- FMMU は「論理アドレス空間の連続領域」を「スレーブ内の物理アドレス空間の連続領域」にビット単位でマッピングします（Section I 第7章）。
- ET1100 は **FMMU を8チャネル**持ちます（`0x0600`〜、1チャネル16バイト）。
- アクセス種別（読み／書き／読み書き）をチャネルごとに設定できます。
- **FMMU の設定は EtherCAT マスタが行います。** RZ/N2L 側ソフトウェアが FMMU レジスタを能動的に書くことは通常ありません（マスタが ESI/ENI 情報を元に設定）。ソフトウェアが知っておくべきなのは「FMMU 経由で自分のプロセスデータ RAM のどこが読み書きされるか」だけです。

## 1.5 SyncManager（マスタ⇔ローカルアプリケーションの安全なデータ交換）

ET1100 内の同じメモリを EtherCAT マスタとローカルアプリケーション（RZ/N2L）が
無秩序にアクセスすると、データの一貫性が壊れます。**SyncManager（SM）** がこれを解決します
（Section I 第8章）。ET1100 は **SyncManager を8個**持ちます（`0x0800`〜、1個8バイト）。

2つの動作モードがあります。

| モード | 用途 | 動作 |
|---|---|---|
| **バッファモード**（3バッファ） | 周期プロセスデータ（PDO） | 常に最新の一貫したバッファを読める。書く方が速くても古いデータは捨てられる（ロスレスではない） |
| **メールボックスモード** | 非周期のアプリケーション層プロトコル（CoE/FoE 等） | ハンドシェイク方式。片方が読み終わるまでもう片方は書けない（データロスなし） |

典型的な構成では、SM0/SM1 をメールボックス（Mailbox Out / Mailbox In）、SM2/SM3 を
プロセスデータ（バッファモード、Outputs / Inputs）に割り当てます。**この割り当ても通常は
EEPROM の初期値かマスタからの設定によって決まり**、RZ/N2L 側は「どの SM がどのバッファ
（アドレス・サイズ）を指しているか」を把握して読み書きするだけです。

### 1.5.1 「共有メモリ感覚」で使えるのはどこまでか

バッファモード（SM2/SM3、プロセスデータ）は、RZ/N2L から見ると確かに
「EtherCAT マスタと自分の間の、勝手に更新される共有メモリ」のように扱えます。
ただし、正確には次のような限定が付きます。

- **共有相手は「マスタとこのスレーブ」の1対1**であり、ネットワーク上の他スレーブと
  直接メモリを共有しているわけではありません。8KB のプロセスデータ RAM は
  **このET1100（スレーブ）ローカルの領域**で、マスタは各スレーブのプロセスデータを
  FMMU 経由で1つの大きな論理アドレス空間に**繋ぎ合わせて**扱います
  （スレーブ間で直接やり取りしたい場合は、マスタ側のロジックが仲介します）。
- 「共有メモリ感覚」が成立するのは**バッファモード（プロセスデータ）だけ**です。
  次章のメールボックスモード（CoE 等）はハンドシェイク方式のプロトコル処理であり、
  共有メモリのようには扱えません。RZ/N2L の仕事は実質的に「共有メモリ的な
  プロセスデータの読み書き」と「プロトコル的なメールボックス処理」の**2種類**あります。
- データが更新されるのは**マスタが実際にフレームを送っている間だけ**です。通信が
  途切れれば内容は古いまま残ります（設定によってはウォッチドッグで出力がクリアされます）。
  また、この領域が意味を持つのは基本的に **Safe-Op/Operational 状態のとき**だけです。
- バッファモードは「常に最新の一貫した値」を返す方式であり、途中の値の取りこぼしを
  許容する用途（一般的な周期I/O）向けです。1件も取りこぼせない値をやり取りしたい場合は
  この仕組みだけでは不十分です。

## 1.6 メールボックス通信とアプリケーション層プロトコル

SyncManager のメールボックスモードの上に、非周期のアプリケーション層プロトコルが乗ります
（Section I 8.2.3）。

| 略称 | 正式名 | 用途 |
|---|---|---|
| **CoE** | CAN application layer over EtherCAT | オブジェクトディクショナリへのアクセス、PDO/SDO、Emergency。**最も一般的**、パラメータ設定などに使用 |
| **FoE** | File access over EtherCAT | ファイル（ファームウェア等）のダウンロード/アップロード |
| **EoE** | Ethernet over EtherCAT | 標準 Ethernet フレームのトンネリング |
| **SoE** | Servo profile over EtherCAT | サーボプロファイル（IEC 61800-7） |
| **VoE** | Vendor specific over EtherCAT | ベンダ独自プロトコル |
| **AoE** | ADS over EtherCAT | Beckhoff ADS メッセージ |

多くの一般的なスレーブは **CoE** さえ実装すれば足ります（オブジェクトディクショナリでパラメータや
診断情報を公開）。マイコン側でこれらをフルスクラッチ実装するのは大仕事なので、
`04_software_bringup.md` で述べる**既存のスレーブスタックソフトウェアの利用**を強く推奨します。

## 1.7 EtherCAT の状態機械（AL State Machine）

EtherCAT スレーブは4つの状態を持ち、マスタが遷移を要求します（Section I 第10章）。

```
        Init  ──────────────▶ Pre-Operational ─────▶ Safe-Operational ─────▶ Operational
         │                          │  ▲                    │  ▲                  │
         │                          ▼  │                    ▼  │                  │
         └───────────────────── Bootstrap（任意）            └── 各状態は逆方向にも遷移可 ──┘
```

| AL control (0x0120) / AL status (0x0130) 値 | 状態 | 意味 |
|---|---|---|
| 1 | **Init** | リセット直後の初期状態。メールボックス・プロセスデータとも通信不可 |
| 2 | **Pre-Operational (Pre-Op)** | メールボックス通信は可能。プロセスデータは不可 |
| 3 | Bootstrap（任意） | FoE によるファームウェア更新用の特殊状態 |
| 4 | **Safe-Operational (Safe-Op)** | プロセスデータの入力（スレーブ→マスタ）は有効、出力はまだ反映されない |
| 8 | **Operational (Op)** | 入出力とも有効な通常運転状態 |

- **Init → Op** に直接遷移することはできず、必ず `Init → Pre-Op → Safe-Op → Op` の順で遷移します。
- RZ/N2L 側アプリケーションは、`AL control` レジスタ（マスタからの要求）を監視し、要求された状態に
  遷移する準備（メールボックス設定の反映、プロセスデータマッピングの妥当性確認 等）ができたら
  `AL status` レジスタに実際の状態を書いて応答する、という設計になります。
- エラー時は `AL status` の bit4（エラー表示）をセットし、`AL status code`（`0x0134:0x0135`）に
  エラーコードを書きます。

## 1.8 Distributed Clocks（DC、時刻同期）※概要のみ

複数スレーブ間、および複数スレーブとマスタの間で高精度に時刻同期する仕組みです
（Section I 第9章）。ET1100 は64bit幅のシステムタイムを持ち、伝搬遅延を自動計測して補正します。
モーション制御など複数軸の同期が必要な用途で使いますが、**単純な I/O 用途であれば DC を
使わなくても EtherCAT 通信自体は成立します**。本ドキュメントでは初期のブリングアップに
必須ではないため深入りしません（`05_register_reference.md` にレジスタ一覧のみ記載）。

## 1.9 SII EEPROM と ESI（スレーブの「名刺」情報）

ET1100 には必ず I²C の外付け EEPROM（SII EEPROM）を接続します（Section I 第11章、
Section III 第8章）。ここには次の情報が入ります。

- **ESC configuration area A/B**：PDI の種類（今回は「非同期 8/16bit µC」）、DC 設定、
  Configured Station Alias など、**電源投入直後に ET1100 自身が自動的に読み込んでハードウェアを
  設定する**情報（word 0〜7、必要なら 40〜47）
- **ESI (EtherCAT Slave Information)**：Vendor ID・Product Code・Revision・Serial Number、
  カテゴリ情報など、**EtherCAT マスタがこのスレーブを識別・設定するための情報**

このため、**RZ/N2L 側のアプリケーションコードを書く前に、EEPROM の内容（＝ハードウェア構成）を
確定する必要があります**。詳細は `04_software_bringup.md` の EEPROM/ESI の章を参照してください。

## 1.10 まとめ：RZ/N2L ソフトウェアが実際にやること

1. 起動後、ET1100 が EEPROM を読み込み終わる（`EEPROM_LOADED` / `0x0110[0]`）のを待つ
2. `AL control`（マスタからの状態要求）をポーリングまたは割り込みで監視する
3. 要求された状態に応じて、メールボックス（SyncManager 0/1）や CoE オブジェクトディクショナリを処理する
4. プロセスデータ（SyncManager 2/3、プロセスデータ RAM `0x1000`〜）を周期的に読み書きする
5. `AL status` / `AL status code` で応答する

これらのレジスタ・メモリへの**読み書き手段**が、次章以降で説明する RZ/N2L の外部バス（SRAM 空間）
経由の PDI アクセスです。
